# Upgrades follow the version skew policy step by step; changes Lodia initiates roll in each tenant's maintenance window, a bounded number of tenants at a time

Decided 2026-10-25.
Built: the steps of a minor upgrade below, its rehearsal among them, Lifecycle driving them, the operator revision, the holds of Workloads, Tenant and the Datastore controller, the stamps on the Deployments and the `Etcd`, Lifecycle's grant of the running revision, of patch updates and of edits of the `DatastoreClass` by the rules below (windows, the fleet, maintenance on request and the settling time), and the warning of the end of support in `Progressing`'s message, a metric and an alert.
Not built yet: the rendering of a dropped minor, in the release that first drops one ([todo](../../todo.md#releases-and-tooling)).

## Decision

**One target; each renderer follows what runs.**
Lifecycle writes one `status.target.version`: the version the API server rolls to now, one minor at a time towards `spec.version`; a spec several minors ahead goes through the newest patch of each minor between, as the version table names it.

- Workloads renders the API server, and konnectivity-server beside it, at `target.version`, and the controller manager and the scheduler at `status.components.apiServer.version`, the version every API server replica runs, or at `target.version` while none is reported.
- Tenant renders every object inside the tenant at the oldest of the three components' versions.
- Each reports what it rolled out in full, in `status.components` and `status.addons` ([status](../api/controlplane.md#status)).
- `status.kubernetes.version` is the oldest of those four.
  It moves only once the last step is done, and it is the version Cluster API reads as the control plane's: the minimum, "more specifically the API server version" ([control-plane.md](https://github.com/kubernetes-sigs/cluster-api/blob/v1.14.3/docs/book/src/developer/providers/contracts/control-plane.md#L455-L457)).

**A minor step.**

1. Preflight, once every part reports the current target (what rolled before it, a patch downgrade among them, finishes first): the next minor is in the version table (else `Unsupported`); `DatastoreReady` at the object's generation (else `WaitingForDatastore`); every kubelet at most three minors older than the next minor, from `status.nodes.oldestKubelet` (else `WaitingForNodes`, also while `status.nodes` is absent or `truncated`, since a partial list tells nothing of the oldest kubelet); no hold of the controller manager (else `ControllerManagerHeld`).
2. `status.kubernetes.upgrade.step` becomes `Rehearsal`, and a copy of the API server at the next minor, on a fresh snapshot of the etcd, has to start and list every resource the tenant lists: `Rehearsed` `Passed` for the step's version at the object's generation ([rehearse-a-minor-step](rehearse-a-minor-step.md)).
   Any other verdict at that generation stands the upgrade `Failed` at `Rehearsal`, with the API server untouched; the rehearsal runs again at once on a new generation, and otherwise as [rehearse-a-minor-step](rehearse-a-minor-step.md) says.
   With `fleet.maxConcurrentRehearsals: 0` the step goes on at once, and `Progressing` says that no rehearsal ran unless one passed for the step's version at the object's generation.
3. `status.kubernetes.upgrade.step` becomes `Backup` in the same write as the step's rehearsal passes, and the `Backup` `<cp>-pre-upgrade-v<minor>-<ControlPlane UID>` (`PreUpgradeBackupName`) completes; a tenant steps to a minor once, so a `Backup` named for the minor does not change with the patch the step goes to, and the name's UID keeps a predecessor's from standing in for it, since a `Backup` outlives its source.
   A failed `Backup` is `Failed`, and deleting it takes another; it has no owner reference, since it must outlive the tenant.
   The target moves once it completes, or once it reports that the class has no backup store, which `Progressing` then says, unless the upgrade stands `Failed` (below); `step` becomes `APIServer` in the same write.
   It moves only while `Rehearsed` is `Passed` for the step's version at the object's generation: a generation that moved during the `Backup` step records `Rehearsal` again, and the `Backup` that completed stands for the step once the new generation passes, since a spec edit changes no data.
   The write that moves it carries the `resourceVersion` of the object it was decided from, so that an edit made in between conflicts and the next pass decides at the new generation.
4. The API server rolls; the step is done when every replica runs the new template, updated and ready, since `/readyz` reports no version.
5. The controller manager and the scheduler roll.
6. In the tenant, kube-proxy, CoreDNS and konnectivity-agent move to the new minor's versions; done when they are applied.
   Their pods roll on the owner's nodes and are reported in `AddonsAvailable`, not awaited.
7. `status.kubernetes.version` becomes the new version.
   Nodes are the owner's: `status.nodes` reports how many run an older kubelet, and nothing forces them.

A patch step has no preflight, no rehearsal and no `Backup`: the target moves at once, keeping the `startedAt` of a change under way.
No step waits for a leader: a hold of the controller manager blocks only the start of an upgrade.
A step that fails — a Deployment past its progress deadline (`APIServerReady`, `ProgressDeadlineExceeded`), or a refusal on an input of `Ready`, an object the API server refuses or another owner keeps, the authentication configuration or a class's missing credentials Secret — stops the upgrade, `Progressing=False`, `Failed`, with the step in `status.kubernetes.upgrade`; it resumes when the cause is gone.
Restoring the pre-upgrade `Backup` into a new `ControlPlane` at the old version is the documented rollback, and it replaces the cluster ([restore-replaces-the-source](restore-replaces-the-source.md)).

**Patch updates.**
Lodia never writes `spec`: `maintenance.autoUpdate.kubernetesPatch` moves `target.version` ([the field](../api/controlplane.md#spec)).
A patch update is pending while `spec.version` is of the target's minor and the newer of it and the table's `latest` of that minor is newer than the target; the grant moves the target there as an owner's patch edit does.
With patch updates the target only moves up: an owner's edit of `spec.version` within the minor still moves it at once, and one below a patch update leaves it where it is.
`spec.version` takes any patch of a minor in the table: `latest` is what updates move to, not an allowlist.

**Class edits.**
An edit of a `DatastoreClass` is pending for each tenant whose `Etcd` runs the class, while the class's UID and generation are not `status.target.datastoreClass` ([the field](../api/controlplane.md#status)): a class deleted and created again under its name starts again at generation 1, so a generation alone would read it as granted, and every tenant on it would take it at once.
The Datastore controller applies a class to an existing `Etcd` only at that UID and generation, holding it whole as it holds a class whose credentials it cannot copy, and copies the credentials meanwhile as under the operator hold; a new `Etcd` takes the class as it is.

**A repair after a restored member.**
A member of the tenant's etcd that etcd-backup-restore restored from snapshots, or that started empty, comes back at revisions the API server's watch cache has already seen: the sidecar restores without bumping the revision ([restorer.go](https://github.com/gardener/etcd-backup-restore/blob/v0.45.3/pkg/snapshot/restorer/restorer.go#L194-L202)), the API server's watches resume after the last revision they saw ([watcher.go](https://github.com/kubernetes/kubernetes/blob/v1.37.2/staging/src/k8s.io/apiserver/pkg/storage/etcd3/watcher.go#L469-L476)), and etcd keeps a watch that starts past its current revision waiting for that revision ([watchable_store.go](https://github.com/etcd-io/etcd/blob/v3.5.27/server/mvcc/watchable_store.go#L136-L141)).
So until the API server restarts its cache lists objects etcd no longer holds and misses later writes, and the controller manager and the scheduler keep what it served until they restart after it.
The Datastore controller's sampler tells such a member by its cluster ID, the term of its last applied entry and its revision less its raft index ([metrics-are-part-of-the-api](metrics-are-part-of-the-api.md)), the Datastore controller records it in `status.memberRestore`, and Workloads rolls the API server, then the controller manager and the scheduler, once per record ([the fields](../api/controlplane.md#status)).
The record and each component's report only move forward, which the API server enforces, so a previous leader's late status apply cannot move them back; its late write of a Deployment, which carries no `resourceVersion`, can still roll the component once more to the template it rendered from an older record, or none, and the next leader's pass on that update rolls it forward again; every status apply of the Datastore controller carries the `resourceVersion` of its pass's read, so a previous leader's record decided before the next leader's does not land over it ([independent-controllers](independent-controllers.md)).
This roll is not a change Lodia initiates: it changes no spec and nothing a release renders, and only an event in that tenant's own etcd starts it.
It rolls now, on a tenant Workloads holds too, where a pass past its waits writes only the annotation `lodia.io/member-restore-detected-at` into the stored Deployments' pod templates, and it takes no slot of the fleet.
A held tenant whose target is of a minor the running revision does not run, which rule 2 never grants, has no such pass, and one whose API server reports such a minor rolls only the API server; the runbook's hand roll covers both, every other roll Workloads cannot write, and a restore the sampler misses, as it can for a member restored again, or started empty, within minutes of an earlier restore, or one no operator replica had seen the previous data of ([Lost etcd quorum](../operations.md#lost-etcd-quorum)).

**End of support.**
Each minor in the version table has an end-of-support date, and a minor dropped from the table stays renderable for one more release, as the source of an upgrade.
Tenants nearing the date are warned in a metric, an alert and `Progressing`'s message, which says it from 60 days before the date of the minor of `status.kubernetes.version`, the dates of [kubernetes.io/releases](https://kubernetes.io/releases/).
A forced upgrade at the end of support, as Gardener forces the next minor of an expired version ([reconciler.go](https://github.com/gardener/gardener/blob/v1.154.0/pkg/controllermanager/controller/shoot/maintenance/reconciler.go#L696-L720)), can come later as an operator policy, off by default.

**The operator revision.**
An operator release renders differently, and so does an operator with another configuration.
`operatorRevision` is `<build version>+<digest>`.
The build version covers what is fixed at build: the version table, the registry and the default resources.
The digest covers what a render reads at run time: the images of `lodia-signer` and `lodia-tunnel`, etcd-druid's version, and the namespaces of etcd-druid and of the operator, which each etcd's NetworkPolicy renders.
Whether the management cluster serves Gateway API is left out: a tenant waiting for it must not then wait for a window.
The configuration's `versions` and `registry` keys join the digest when something reads them ([operator configuration](../README.md#installation)).
Revisions are compared for equality only, so a rollback of the operator is one more revision.
Workloads, Tenant and the Datastore controller render with the running revision only while `status.target.operatorRevision` equals it ([what they hold until then](../api/controlplane.md#status)).
Workloads stamps the revision on its Deployments and the Datastore controller on the `Etcd`, in the annotation `lodia.io/operator-revision`, never in a pod template, so a revision that changes nothing rolls nothing.
Until the grant Workloads writes nothing that exists but the deletions [`target.operatorRevision`'s row](../api/controlplane.md#status) names and the annotation of a repair after a restored member (below), and creates what is missing: it keeps no inventory, so an object a new release adds is created at once.
Until the grant Tenant writes nothing that exists inside the tenant but the tunnel's renewed client certificate, neither the inventory nor a prune; it creates only what the stored inventory lists and the tenant lacks, so an object a new release adds waits for the grant, and a listed one the release no longer renders stays as it is.
Tenant stamps nothing: `status.addons.operatorRevision` is the revision of a pass that applied in full.
Until the grant the Datastore controller applies the `Etcd` it finds, with only a new generation of the etcd certificates, and writes the etcd's NetworkPolicy only when it is missing; it creates a missing `Etcd` from the full render, stamped with the running revision.
etcd-druid's automatic spec reconcile is off, and the Datastore controller asks for each reconcile ([dedicated-etcd-by-default](dedicated-etcd-by-default.md)): for each generation and stamp of the `Etcd` until a reconcile that started after the request has served it, and for a stamp it has not asked under before only once etcd-druid's Deployment runs the version the operator was given and no pod of an older one terminates, since an older etcd-druid would roll the members to its own render.
So `status.datastore.operatorRevision` names a revision only once etcd-druid, at the version that revision names, has reconciled the `Etcd` under it in a reconcile that started after the request, and every member runs that spec, wherever `DeploymentReplicaSetTerminatingReplicas`, on by default from Kubernetes 1.35, lets the Deployment count a terminating pod ([A tenant namespace](../README.md#a-tenant-namespace)).
A hand edit is not reverted while a tenant waits; storing the last render, as Gardener's ManagedResources do, stays a later option with the same contracts.
A held renderer carries no refusal: what it reports is what its pass sees.
While a condition it writes holds a refusal, a reason of `Refused`, `ObjectsControlledElsewhere`, `AuthenticationInvalid`, `SecretNotFound` or `RefusedBeforeHold`, or is not True, which may end its message with a refusal under its own reason, its held pass also sends every write the grant's first pass would send but the Datastore controller's request below, the running revision's render as the same server-side apply under the same field manager with force, by dry run (`dryRun: All`), and runs Lodia's own checks that stand for the API server's on that render, the validation of the authentication configuration among them.
Workloads sends its Service, ConfigMaps, NetworkPolicies, Deployments and PodDisruptionBudgets, and the routes that differ from the render, but a Deployment that mounts a ConfigMap whose dry run is refused; the Datastore controller sends the `Etcd` it renders, stamped with the running revision, the etcd's NetworkPolicy, and the class's credentials copy while it keeps one on another store and the class waits for no grant of its own; Tenant sends, through the tenant's API server, every write of its pass, the inventory's, each object's and each prune's.
The Datastore controller's request that etcd-druid reconcile the `Etcd` under the new stamp, a merge patch, is not tried: a held pass sends its own request for real while one is due, as every pass does, and meets its refusal there, so a refusal of it found before the hold reads as gone on a pass that sends none, as while the request waits for etcd-druid's Deployment, and the grant's request first meets the API server in the grant's slot.
A dry run passes admission as the write does: a `ResourceQuota` refuses it without recording usage ([controller.go](https://github.com/kubernetes/kubernetes/blob/v1.37.3/staging/src/k8s.io/apiserver/pkg/admission/plugin/resourcequota/controller.go#L239-L249)), a `ValidatingAdmissionPolicy` evaluates it, and an admission webhook whose `sideEffects` are `None` or `NoneOnDryRun` is called ([dispatcher.go](https://github.com/kubernetes/kubernetes/blob/v1.37.3/staging/src/k8s.io/apiserver/pkg/admission/plugin/webhook/validating/dispatcher.go#L248-L255)); the same lines hold at 1.36.7 and 1.35.11.
A dry run the API server refuses is a refusal under its own reason, which names the grant's write that would be refused and why and holds every grant, since the pass tries it again on every pass; with every dry run accepted the refusal is gone on that pass, and the condition reports what runs, as at rest.
Workloads' held wait for `CertificatesReady` or `DatastoreReady` tries too, while a condition of Workloads holds a refusal or is not True and `APIServerReady` is one a wait counts, the availability of what runs or a refusal: it renders past what it waits for, writes nothing, and reports the count with what the trial finds, so a count that dips and recovers inside one wait, a lost quorum's, names the refusal again, False and then True under it; over a refusal at the object's generation that reports no availability, Workloads' wait for the grant under a refusal or a refused creation, it reports the wait for the grant with what the trial finds, as a held pass does.
A held wait that cannot build the render, without the Datastore's endpoints, with a Secret not hashed yet or without a Ready node at a `nodePort` endpoint, tries only the Service and the routes and keeps a condition that is not True as it is, so the first pass past it tries, and a True one may still fall to False on its count; so one pass without a Ready node at a `nodePort` endpoint leaves a tenant that serves as it was, and the next pass counts it again.
A held wait on a target the running operator's table does not hold counts what runs, as a wait at the granted revision does: no pass past it comes under that revision, since Lifecycle grants nothing over such a target (rule 2), and the next revision's render is its own.
What a held pass or a held wait finds ends a condition it builds anew, a count, a wait at the object's generation or Workloads' wait for the grant, and never one it keeps as it is, which describes the generation it last did; Lifecycle decides from reasons and statuses alone, so it loses nothing.
Over Workloads' wait for the grant, `WaitingForTarget` at the object's generation, a refusal the check or the trial finds takes its own reason under False, `AuthenticationInvalid` or `Refused`, which holds every grant (rule 4), while a write no dry run can try alone leaves the wait.
The Datastore controller writes `DatastoreReady` from what each pass sees, False on each wait after the first grant, and Tenant's waits keep `AddonsApplied` under a refusal's reason and write no True, so the first held pass past a wait of either tries.
A webhook with any other `sideEffects`, which the API server takes only from a configuration stored before `admissionregistration.k8s.io/v1` required one of those two ([validation.go](https://github.com/kubernetes/kubernetes/blob/v1.37.3/pkg/apis/admissionregistration/validation/validation.go#L219-L228)), answers every dry run that it does not support dry run, whatever its `failurePolicy`: that answer is no verdict, and the condition reports `RefusedBeforeHold`, a refusal that no dry run can try, naming the webhook as the API server answers.
Only a management cluster can hold such a configuration: a tenant's etcd starts empty at a minor Lodia runs, or from a `Backup` of a `ControlPlane`, so every configuration in it was created under that rule, which an update keeps ([validation.go](https://github.com/kubernetes/kubernetes/blob/v1.37.3/pkg/apis/admissionregistration/validation/validation.go#L727-L751)), and Tenant's dry runs never get that answer.
A dry run that gets no answer writes no status: no answer is no observation.
A refusal the held pass meets itself, a creation it sends or another owner's object it checks, keeps its own reason as before, and comes first in the message ([the reasons](../api/controlplane.md#conditions-and-their-reasons)).

**The grant.**
Lifecycle grants what is pending, the running revision, a patch update and an edit of the tenant's `DatastoreClass`, by these rules in their order:

1. A new value of `lodia.io/maintain-requested-at` is recorded in `status.maintenance.lastHandled` on every pass but a paused or deleting one's, pending or not; a value over 256 characters is not handled, and removing the annotation leaves the record, so the same value set again does nothing.
2. A revision that does not run the minor of the target or of a reported version is granted on no path, since a renderer would write `WaitingForTarget` and take a running tenant down: `Unsupported`; a tenant in a slot keeps it, so the release after reaches it at once.
3. At once, with no slot, the revision: no target yet; an edit of `spec` not taken up, its generation ahead of `Progressing`'s; an upgrade its owner started; a new value of the annotation; a tenant in a slot, which keeps it, so that a later release, or a rollback, reaches a tenant a bad release left failed; and three kinds of tenant only the grant brings back to `Ready`, since a held renderer cannot: `AddonsApplied` not True with no `status.addons.version` or with `Applying`, `APIServerReady` False, `WaitingForTarget`, at the object's generation, and a restored `ControlPlane` whose controller manager is not released.
   A patch update goes at once only with no target yet, on a new value of the annotation and in a slot, and an edit of the class only on a new value of the annotation and in a slot.
4. Not while `Unsupported` or `Failed` stands, a refusal on an input of `Ready` at rest included: the owner's to fix.
   Every refusal holds every grant, since its writer tries it again on every pass, a held one by dry run, but `RefusedBeforeHold`, a refusal no dry run can try, which holds no grant of the running revision while that revision is pending, since only the grant tries it.
   That revision is granted by the rules below, as any change to a tenant that serves, with everything else pending in the same slot, a patch update and an edit of the class, and the refusal stays in its condition, `Ready`'s reason and `Progressing` `Failed` meanwhile, each naming a refusal that holds the grant before it.
   From the grant the change is `MaintenanceFailed` while the refusal stands, also until the writer's first pass at the granted revision, which ends it or meets it again; a refusal that stands keeps the slot, as any failed change does.
5. Not while `TimeZoneUnsupported` stands; outside the window, `WaitingForWindow`, with `target.scheduledFor` its next start.
6. Not while `Ready` is not True, at whatever generation each input describes, `AddonsApplied` left out while it waits with `AccessReady` True: `Ready`'s reason, or `WaitingForReady` while `Ready` is Unknown, whose reasons say something else under `Progressing` False; `Ready` True under a refusal's reason is True, since the tenant serves.
   A held Tenant keeps `AddonsApplied` at the generation it describes for the whole hold, so `Ready` at the object's generation would never grant an edit Tenant had not taken up when the release started.
   Nor while `ProgressDeadlineExceeded` stands on an available component: that reason, since the change would fail in the write that grants it, for a cause it did not bring.
7. A slot in the order of the queue, for everything still pending: `Maintaining`, in the same write as the grant; none, `target.scheduledFor` when the tenant became eligible, which queues it, and `FleetLimit` unless a reason ranked above it applies.

A change Lodia started keeps its origin in `status.maintenance.slotSince`, written in the same write as the grant: the tenant holds its slot while it is present, whatever `Progressing` says, so a reason ranked above the slot's does not free it; a grant on request is the owner's.
Only the change settling and deletion end a slot: an owner's edit that the writers take up before the change settles rolls in the slot and settles it as any other change, and a paused tenant keeps counting as a used slot, since a tenant a bad release left failed would otherwise leave the fleet on an edit or a pause, and rule 6 would keep the next release waiting for a `Ready` only that release brings.

**Who waits for the window:**

| change | when it rolls |
|---|---|
| the owner edits `spec` | now, and the pending revision with it |
| `maintenance.autoUpdate.kubernetesPatch` finds a newer patch | in the window |
| a new operator revision renders something else | in the window once no refusal stands, also over `RefusedBeforeHold`, which the grant tries; a held renderer tries the grant's writes only while its condition holds a refusal or is not True, so this is no preflight of the release: a refusal the release brings meets its first tenants in their slots, and the fleet limit stops it there |
| an edit of the tenant's `DatastoreClass` that reaches its `Etcd` | in the window: a class is shared, and the edit rolls every member on it |
| a certificate renewal that needs a restart | now, or at the grant on a tenant Workloads holds; in the window with phase 3's rotations |
| a credential rotation the owner started | now; the stages wait for the owner |
| a member of the tenant's etcd restored from snapshots or started empty (`status.memberRestore`) | now, on a held tenant too, with no slot: a repair, not a change (above) |

**Windows.**
`spec.maintenance.window` ([the field](../api/controlplane.md#spec)) is read with the zone database embedded in the operator (`time/tzdata`); a window inside a repeated hour opens once.
Without a window Lodia-initiated changes roll at any time, still within the fleet limit.

**The fleet.**
Across all tenants, at most `fleet.maxConcurrentRollouts` (operator configuration, 5 by default) roll a Lodia-initiated change at once.
A repair after a restored member takes no slot and counts for none.
A tenant holds a slot while `status.maintenance.slotSince` is present, whatever `Progressing` reads: a failed rollout Lodia started keeps its slot, so that many failures halt maintenance across the fleet, as unavailable pods halt a Deployment's rollout, which the alert [`LodiaMaintenanceHalted`](../operations.md#lodiamaintenancehalted) reports.
Tenants get slots in the order of `status.target.scheduledFor`, then namespace and name, as far as the cache shows them: a grant can pass a tenant whose `scheduledFor` the cache does not show yet, never the limit; a tenant is queued while its `scheduledFor` is at or before now, whatever `Progressing` says, since a wait for a slot can sit under a reason ranked above `FleetLimit`, and a pass grants when the tenants that hold a slot and those queued before it are fewer than the limit, counted from the cache and, before the grant is written, again under a lock: from the fleet the API server lists until a grant the running operator wrote has shown in its cache, and again after a grant whose outcome is unknown or that its cache did not show within 10 seconds, and from the cache otherwise.
Each grant waits until the cache holds it before the lock is released, and a watch streams a kind's changes after the `resourceVersion` it starts at and resumes after the last one it returned, missing none ([api-concepts.md](https://github.com/kubernetes/website/blob/snapshot-initial-v1.37/content/en/docs/reference/using-api/api-concepts.md#L404-L413)), and client-go's informer, which the cache is, puts each in its store in the order it arrives ([reflector.go](https://github.com/kubernetes/client-go/blob/v0.37.1/tools/cache/reflector.go#L1006-L1075); [`InOrderInformers`](https://github.com/kubernetes/client-go/blob/v0.37.1/features/known_features.go#L127-L130), GA and locked on), and the list of a relist, which follows a watch it cannot resume, at once ([reflector.go](https://github.com/kubernetes/client-go/blob/v0.37.1/tools/cache/reflector.go#L911-L916), [controller.go](https://github.com/kubernetes/client-go/blob/v0.37.1/tools/cache/controller.go#L999-L1002), [L1075-L1081](https://github.com/kubernetes/client-go/blob/v0.37.1/tools/cache/controller.go#L1075-L1081); [`AtomicFIFO`](https://github.com/kubernetes/client-go/blob/v0.37.1/features/known_features.go#L112-L114), Beta, on by default and not locked, without which the listed objects reach the store one by one, [the_real_fifo.go](https://github.com/kubernetes/client-go/blob/v0.37.1/tools/cache/the_real_fifo.go#L604-L619)), so the cache then holds every grant written before, a previous leader's included: two passes never take one slot.
The operator refuses to start while client-go reports either gate off, as an environment's `KUBE_FEATURE_AtomicFIFO=false` would make it ([envvar.go](https://github.com/kubernetes/client-go/blob/v0.37.1/features/envvar.go#L169)).
An owner's change takes no slot; a minor step's rehearsal takes a place among `fleet.maxConcurrentRehearsals` of its own ([rehearse-a-minor-step](rehearse-a-minor-step.md)).
A change Lodia started holds its slot while it rolls: a part not at the target, a replica or member not updated, a renderer that reports neither the granted revision nor the running one, an `Etcd` that runs another UID or generation of its class than the one granted, which `status.datastore.class` reports, as the revision, only once etcd-druid has rolled it, but as applied while no revision is reported or the applied `Etcd` records a class the report does not name, as after an `Etcd` was created again from another class, or no edit could reach it.
A Tenant that waits after the grant, `AddonsApplied` False with a `WaitingFor*` reason while `AccessReady` is True, keeps its earlier `status.addons`, so the change stays `Maintaining` with its slot until the wait ends: such a wait names no cause of the change.
Once it has rolled out, `status.maintenance.settlingSince` records when, and the slot is held for a settling time S after the later of that and `Ready`'s last transition: `health.failuresBeforeFalse` × (`health.period` + Health's timeout) + one etcd-druid status sync, `--etcd-druid-status-sync-period`, which the chart renders from the period it gives etcd-druid ([Installation](../README.md#installation)), 45 seconds at the defaults.
Then the slot is free while `Ready` is True, and the change is `MaintenanceFailed` while it is not; a refusal among `Ready`'s inputs, an object refused or kept elsewhere, the authentication configuration or a class's missing credentials Secret, or `ProgressDeadlineExceeded`, fails it at once.
A canary, one tenant first for each new revision, can come later without a change of contract.

**Maintenance on request.**
The annotation `lodia.io/maintain-requested-at: <token>` on a `ControlPlane` grants its pending maintenance now ([the field](../api/controlplane.md#spec)).
Lodia never removes the annotation, so a GitOps tool that keeps it does not fight Lodia; it works like the `kubectl.kubernetes.io/restartedAt` that `kubectl rollout restart` writes ([objectrestarter.go](https://github.com/kubernetes/kubernetes/blob/v1.37.1/staging/src/k8s.io/kubectl/pkg/polymorphichelpers/objectrestarter.go#L41)).

**`Progressing` says where a change stands**, by the reasons and order in the [field reference](../api/controlplane.md#conditions-and-their-reasons); it is the one home of the reason a target lags `spec`.

## Why

- The [version skew policy](https://kubernetes.io/releases/version-skew-policy/) allows the controller manager and scheduler to lag the API server by one minor and kubelets by three, never the other way round; the order above is the only safe one, and in-tenant components cannot be newer than the API server.
- A renderer that follows what runs keeps the skew by construction: kubeadm upgrades the addons only once every API server runs the new version ([addons.go](https://github.com/kubernetes/kubernetes/blob/v1.37.1/cmd/kubeadm/app/cmd/phases/upgrade/addons.go#L62-L73)), and HyperShift rolls a component only once its dependencies are available at the desired version ([status.go](https://github.com/openshift/hypershift/blob/v0.1.86/support/controlplane-component/status.go#L59-L101)).
  A bug in Lifecycle's sequencing then cannot break the skew, and the current step is derived from what runs on every pass, but for `Rehearsal` and `Backup`, which are recorded: while they run what runs is identical to a finished step, so nothing would derive them, and the preflight would run again.
- A snapshot before every minor upgrade is the only rollback etcd allows: a minor downgrade of the API server is unsupported.
- In the solutions we studied, a new operator release can re-render every cluster it manages at once; one bug or one changed default then becomes a fleet-wide rollout in the middle of a business day.
  Gardener answers with maintenance time windows ([shoot_maintenance.md](https://github.com/gardener/gardener/blob/v1.154.0/docs/usage/shoot/shoot_maintenance.md#L11-L20)) and a cap on the shoots each gardenlet reconciles at once ([types.go](https://github.com/gardener/gardener/blob/v1.154.0/pkg/apis/config/gardenlet/v1alpha1/types.go#L315-L319)); the same two levers are enough here.
  Counting a failed rollout in its slot makes the cap a brake on a bad release too.
  Without the settling time a revision that changes no template is reported within seconds and frees its slot before a probe can fail, so a release that breaks tenants would reach all of them.
- Every renderer is held, not only pod templates: a re-rendered NetworkPolicy, kube-proxy configuration or `Etcd` is as fleet-wide as a pod template.
- A repair after a restored member rolls at once because the wait is the defect: until the API server restarts it lists objects etcd lost and misses writes, and the tenant's controllers act on that, while a certificate renewal can wait for the grant because the certificate it replaces stays valid for a third of its lifetime.
  The roll surges and keeps serving, as every roll of the three does, and it follows only a member's new data life, which no release renders; a fleet limit would queue real repairs behind each other and only spread over hours the rolls a defect of the rule would start, each of which reports a loss.
- A held renderer under a refusal tries the grant's writes by dry run, so the refusal it reports is the one the grant would meet now: a person who removes the cause sees it end on the next held pass, and the release then comes in the window, while a refusal that stands holds the grant, which would only fail in its slot.
  It tries them while its condition is not True too: a pass that finds what it reports not serving keeps that state's reason and ends its message with the refusal, so a reason alone would drop the refusal after one such pass, an unready replica or a lost quorum, and the release would be granted into a slot over a cause that still stands.
  A held wait tries them as well: one that sent nothing would report its count over the refusal it keeps, so a count that dips and recovers inside the wait would end the refusal with no trial, and the release would be granted into a slot over it; a wait that cannot build the render has nothing to try, so it raises nothing to True and leaves the trial to the first pass past it; a wait on a target the running operator cannot render has no such pass under that revision, so keeping False there would page for as long as that operator runs and protect nothing.
  What a held pass finds goes on a condition it builds anew, never on one it keeps as it is: that condition still says what the pass found the time before, so the same text would be appended on every pass, each status write bringing the next pass, until the message passed its bound and the API server refused every status write of the tenant.
  A refusal over Workloads' wait for the grant takes its own reason because that wait is granted at once: the grant's first write is the one the dry run found refused, and the rest of the release would roll on a tenant that serves outside its window and the fleet limit; a refusal under `AddonsApplied`, a refused object or another owner's, is one a held Tenant meets or tries on every pass, so it holds the grant as any refusal does.
  One pass without a Ready node at a `nodePort` endpoint, which comes only once no node reports the published address, keeps that address and waits as the other waits do, so a node that comes back with it keeps it: a wait that replaced the availability it reports made the next pass wait for the grant, which rule 3 grants at once, so a tenant that serves would be granted outside its window though its endpoint had not changed.
  A dry run sends nothing for real and passes the API server's admission as the write does; it is sent only while a condition holds a refusal or is not True, so a held tenant at rest, every condition True under its own reason, costs no request more.
  A refusal no dry run can try, a webhook's that does not support dry run, waits for the window and a slot, not for a person: only the grant tries it; the window still protects a tenant that serves, and the slot counts a change that fails on it as any other.
- Automatic patch updates in the window keep tenants on supported versions without a platform on top polling for releases; the version table, not `spec`, carries them, since a GitOps tool would revert a written `spec`.

## Rejected

- Rendering every tenant immediately on operator upgrade — simplest code, fleet-wide risk.
- One operator version per tenant (the HyperShift control-plane-operator shape) — the strongest isolation of renderer versions, at the cost of a pod per tenant and a second upgrade path.
- Automatic minor upgrades — a minor can break workloads (removed APIs); the owner opts in by editing `spec.version`.
- A target per step — a central state machine for what each renderer can derive from what runs.
- Waiting at step 4 for the controller manager and the scheduler to have a leader — Cluster API's control plane checks their pods and etcd between steps, not a leader ([preflight.go](https://github.com/kubernetes-sigs/cluster-api/blob/v1.14.3/controlplane/kubeadm/reconcilers/kubeadmcontrolplane/preflight.go#L170-L178)), and a hold would stall an upgrade under way.
- Comparing operator versions as older and newer, or stamping them in pod templates — a rollback has an older version, and a stamp in a template rolls every tenant on every release.
- `status.target.reason` — it repeated `Progressing`'s reason.
- Granting the running revision at once, with no slot, over a refusal no dry run of a held renderer can try — a tenant that serves would roll outside its window and the fleet limit, also for its own administrator's webhook that cannot be called.
- Lifecycle telling a refusal a held renderer carries by the condition's type and status — the same conditions hold refusals a held pass meets itself, a creation it sends again or another owner's object it checks, which would be granted while their writer retries them, and a refusal the writer has seen end would stay.
- A held renderer that drops a refusal it cannot send again — its condition, `Ready` and `Progressing` would stop naming a refusal that may still stand.
- A held renderer that carries a refusal it found before the hold, as the text of its previous condition, read back on every pass, until the grant — a branch that writes another message, a message cut at its bound, a refusal worded otherwise, a count left over and a case the carry did not convert each lost the refusal or kept one whose cause was gone, and a carried refusal was granted in the window over a cause that still stood, failing the change in its slot.
- A dry run of the grant's writes on every held pass — every held tenant would send its whole render again on every pass, for refusals that are not there.
- A dry run only while a condition holds a refusal's reason — one held pass that writes a False under the writer's own reason, a replica unready or a lost quorum, ends the trial for the rest of the hold, and the release is granted into a slot over the refusal.
- Keeping every condition that is not True through any held wait — a tenant is held for the whole time between a release and its window, so a quorum lost and half regained, with one member down for hours, would keep `APIServerReady` False for hours on a tenant that serves, and whoever reads it would look for the fault in the wrong place.
- Keeping a condition that is not True through a held wait on a target the running operator cannot render — no pass past that wait comes under that revision, so `APIServerReady` would stay False on a tenant that serves, and page through `Ready`, for as long as that operator runs, and protect nothing, since the next revision's render is its own.
- Appending what a held pass finds to a condition it keeps as it is — the text repeats on every pass, each status write brings the next pass, and once the message passes its 32,768 bytes the API server refuses every status write of the tenant.
- Granting at once over an `AddonsApplied` refused or kept by another owner, or over Workloads' wait for the grant under a refusal a held writer found — the grant's first write is the one refused, and the rest of the release rolls on a tenant that serves at whatever time it is.
- Lifecycle writing `spec.version` for a patch update, as Gardener's maintenance writes the shoot's — `spec` has one writer, its owner.

## Consequences

- Lifecycle is the only controller that knows the maintenance windows and the fleet; it counts the tenants rolling a Lodia-initiated change from their `status` (`status.maintenance.slotSince`), not in memory, so a restarted operator neither forgets nor double-counts a rollout in progress.
- `status.target` is part of the API users read: `target.version`, `target.operatorRevision`, `target.datastoreClass` and `target.scheduledFor`, with `Progressing`.
- An operator release note states which tenants will roll (all with a changed render) and what changes, because the roll is deferred, not hidden.

## Code

- `api/v1alpha1` — `Target`, `KubernetesStatus` with `UpgradeStep`, `ComponentStatus` and `Rendered`, `MemberRestoreStatus`, `MaintenanceStatus`, the window's rule, the rules that keep `status.memberRestore` and each `memberRestoreDetectedAt` moving forward, the annotations `lodia.io/operator-revision`, `lodia.io/maintain-requested-at` and `lodia.io/member-restore-detected-at`, `PreUpgradeBackupName` and the reasons of `Progressing`; `test/api` holds the rules.
- `cmd/lodia`, `.ko.yaml`, `internal/operator` — the build version, set by ko from `VERSION` (every build of `cmd/lodia` sets it), and `Inputs.Revision`, which adds the digest; the operator refuses to start on an empty version or a revision longer than the field's 128 characters.
- `internal/controller/lifecycle` — `decide` holds the steps above, the patch update, the class generation the `Etcd` may run and the end of support's notice, and `maintain` the grant, its rules, whose rule 4 passes over `RefusedBeforeHold` while the running revision is pending (`retried`), and which, as `Ready`, names a refusal that holds the grant before one under `RefusedBeforeHold` (`stopping`), and the settling time, reading what is pending from `pending`; `window` reads the window with `time/tzdata`; the reconciler gathers its facts, the `ControlPlane`, the `Backup` of the minor step, the `DatastoreClass` the `Etcd` runs, whose edits a watch maps to the `ControlPlane`s that run it, and, while a change is pending, the fleet from the cache, decides on the cached object, on a change decides again on the object read live, writes a minor step's move of the target under that object's `resourceVersion`, and before a write that takes a slot decides once more under the fleet's fence of `internal/fence`, which honours the pass's deadline, from the fleet the API server lists until a grant has shown in the cache and after a grant whose outcome is unknown or that the cache did not show within 10 seconds, and from the cache otherwise; it requeues at the window's next start, at most an hour ahead, every 30 seconds while `FleetLimit`, and at the end of the settling time.
- `internal/operator` — `fleet.maxConcurrentRollouts`, at least 1, `fleet.maxConcurrentRehearsals`, 0 or more, and the settling time from Health's configuration; `Setup` refuses to start while client-go reports `InOrderInformers` or `AtomicFIFO` off, which `fence.Ordered` checks and `operator_test.go` holds.
- `internal/contract` — `Refusals`, the reasons of a refusal, which Lifecycle stops a change on and a held writer tries the grant under, as under a condition not True; `internal/statusapply` — `Tried`, a held pass's condition with what its dry run found; `internal/apistatus` — `DryRunUnsupported`, the API server's answer that a webhook does not support dry run, which is no verdict.
- `internal/controller/workloads` — `status.components.*.version`, the tag of each component's own image once every replica runs it, and the controller manager and the scheduler rendered at `components.apiServer.version`; the hold in `apply`, which, while `target.operatorRevision` is not `Reconciler.Revision`, writes only an object neither the cache nor the API server holds, and, in `repair`, the merge patch of the annotation `lodia.io/member-restore-detected-at` of a repair after a restored member, its one write into a stored Deployment; `trying`, `try` and `trial`, the dry run of the grant's writes while a condition holds a refusal or is not True, `triesPast`, which a held wait for the certificates or the datastore renders past them by, `keep`, which keeps a condition that is not True through a held wait that a later pass under the running revision passes, the `nodePort` endpoint's included, and says, as `heldAvailability` does, when it keeps a condition as it is, and `trial.over`, which ends a condition built anew with what the check and the trial found, a refusal over the wait for the grant under its own reason; the stamp on the Deployments, which `status.components.*.operatorRevision` reports under the rule of `version`; the annotation, rendered on the API server from `status.memberRestore` and on the controller manager and the scheduler from `status.components.apiServer.memberRestoreDetectedAt` (`rollsFor`), which `status.components.*.memberRestoreDetectedAt` reports once every replica runs a template that carries the value rendered, and otherwise keeps, so a cache behind a finished roll moves no report back (`rolledOut`).
- `internal/controller/tenant` — the render at the oldest component's version, and `status.addons`, the version and the running revision of a pass that applied it in full; the hold in `hold` and `heldInventory`, which, while `target.operatorRevision` is not `Reconciler.Revision`, apply only an object the stored inventory lists and the tenant lacks, and report what runs, and, while `AddonsApplied` holds a refusal or is not True, `applyInventory` through the tenant's API server by dry run.
- `internal/controller/datastore` — `holdClass`, which applies the class to an existing `Etcd` only at `target.datastoreClass`; the hold in `renderEtcd` and `applyNetworkPolicy`, which, while `target.operatorRevision` is not `Reconciler.Revision`, apply the stored `Etcd`'s spec on the newest certificate generation and a missing NetworkPolicy, and report what runs, `tryEtcd` and `trial`, the dry run of the grant's writes while `DatastoreReady` holds a refusal or is not True, and in `storeMoved`, which keeps the credentials copy of the store the `Etcd` names while either hold keeps its class; the stamp on the `Etcd`; `status.datastore.operatorRevision` and `status.datastore.class` from `RolledOut`, and the class from the applied `Etcd` while no revision is reported or the report does not name its class.
- `internal/etcddruid` — `Copy`, the stored `Etcd`'s spec on a new certificate generation; `RequestReconcile`, which asks etcd-druid for each reconcile under the record `lodia.io/etcd-reconcile-requested` until `served` says a reconcile under another run ID has taken it, `inFlight`, its wait while such a reconcile runs, and `druidPending`, its wait for etcd-druid's Deployment.
- `internal/versions` — `Oldest`, `Newer`, `Latest`, `Next`, `Step` and `MinorsAhead`, the version arithmetic of a step and of a patch update, and `EndOfSupport`, each minor's date.
